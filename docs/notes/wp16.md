### Decisions

- **The allowlist fails closed.** It is enforced when `APP_ENV=production`, and also when `APP_ENV` is unset and
  `NODE_ENV=production`. That already covers Zerops (`zerops.yml` sets `NODE_ENV: production`). The list is
  `CONNECTOR_HOST_ALLOWLIST`, or the §6.2 defaults, plus the `APP_URL` host. Entries match exactly, and `*.x` entries
  match sub-domains only.
- **The address guard is stricter than the spec's letter.** The spec asks that the embedded IPv4 of
  mapped/compatible/NAT64/6to4/Teredo forms be unicast. We refuse those forms outright, whatever they embed, and
  require IPv6 to be in `2000::/3`. ipaddr.js has no name for IPv4-compatible `::/96` and would call `::7f00:1`
  "unicast", so that prefix is checked explicitly.
- **The DNS timeout** is the c-ares setting (1.5 s), with a hard backstop 300 ms later. The `timeoutMs` deadline
  starts after DNS, so the worst case is about 1.8 s + 5 s.
- **Pick keys are the full dot path** (`"json.amount"`), so they are flat and cannot collide. text/plain gives
  `data:{}` (the raw text is for the owner only).
- **Secret redaction** also covers upstreams that reflect headers (postman-echo does). This is not in the spec text,
  but a `responsePick` of `headers.authorization` would otherwise hand the secret to the agent.
- **Secret AAD = workspace + name** (not the id), so the Pg upsert can keep the row id. The key version is 1
  (derived) or 2 (explicit). A key change reads as "missing", never as garbage.
- **Limits live in process.** The app is one container, and `connector_calls` has no workspace or host column to
  count by. Rate refusals use `E_CONN_RATE_LIMITED` (local).
- **Dedupe returns only `ok` rows**: a failed first attempt may be retried.

### Decisions

- **The stage gate is one step earlier than WP6's handlers, and both stay.** On the relay path `send_confirmation`
  is simply not in the `pay` stage, so it comes back `not_available` before the handler's `payment_not_confirmed`
  is ever reached. The handler refusal is kept as the fail-safe (a published agent carries all of its HTTP tools
  from the first second, T-D1-5) and is asserted separately in the parity suite.
- **`payment_link` does not `markConnector`.** "The link was sent" is not "the payment succeeded": the kernel's
  `connector_succeeded` exit reads `payment.status === "succeeded"`, so marking it would move the relay out of the
  act stage while the customer is still paying, and a retry would come back `not_available`. The payment row is the
  truth, and it is already persistent.
- **Dedupe is for connector tools only.** With no call id (WP18's gateway) a connector tool replays an `ok`
  `connector_calls` row with the same `(takeoverId, toolName, argsHash)` inside 30 s. The built-ins are pure over
  the case state, so a repeat is harmless — and swallowing a genuine second answer to the same question would be a
  real bug.
- **`connector_calls` logs EXECUTIONS, not tool calls.** A stage-gate refusal, an invalid-args refusal at the
  service layer and an idempotent replay never reach the runtime and leave no row. That keeps §9's "connector
  health: calls, error %, p50 ms" honest.
- **The Simulate fallback is invisible to the agent.** `PaymentService.create` already falls back when Polar is
  down, and `payment_link` still answers `{status:"link_sent"}` — a provider outage is not something the caller can
  act on. The payment ROW carries it (`provider:"mock"`, then `simulated`), and the pay page and console read it
  from the payment view. `ConnectorOutcome.ui` has no `simulated` field, and an earlier comment claiming otherwise
  was wrong and is fixed.
- **One generic Polar customer, not one per relay.** `POLAR_DEMO_CUSTOMERS` is keyed by Baton scenario id; a relay
  has no scenario, so `relay:<slug>` would match nothing and the checkout would ask for name and email too. Relay
  payments pass `scenarioId = "relay"`. A recorded flagship run (`simCallId === null && flagship`) keeps its own
  scenario customer and real policy address.
- **A sample with no address still prefills one.** Without `customerBillingAddress` Polar asks a US buyer for a full
  address (research/12 §12) and the judge types 20–40 s mid-demo. Every gallery sample has a fictional address; one
  that somehow does not falls back to `RELAY_FALLBACK_ADDRESS` rather than dropping the prefill.
- **`setCaseExtras` compares against the STORED state, not the overlaid one** (the fix in the leftover diff). The
  service overlays the flow (stage, disclosures, payment) onto the derived state for its own reasoning; comparing
  the overlay against itself made `sameFlow` always true, so the mirror into `cases.state` never fired and route #4
  and the console saw a stale case. `Ctx` now carries `raw` (what WP3 stores) alongside `state`.
- **The two WP16·1 stand-ins are gone rather than kept in sync.** The connector runtime and the tool service
  validate the SAME connector's arguments; two implementations could have disagreed about what reaches an upstream.

### Decisions

- **The policy decides before DNS, not after.** `checkConnectorHost` runs on the host string, so a refused host is
  never resolved and never dialled. That is acceptance item 1, and it is also the cheaper order.
- **A downgrade does not delete the org's hosts.** It stops them being allowed, and the refusal *names the plan*
  ("…is one of this workspace's allowed hosts, but your current plan does not include custom connector hosts"), so
  an upgrade brings exactly the same relays back to life. Deleting rows on a plan change would make a billing event
  destructive.
- **Being on the list only clears the allowlist gate.** The SSRF guard stays unconditional — address checks, pinned
  DNS, redirect and encoding refusals, byte caps — which is why an org host cannot be pointed at cloud metadata.
  Acceptance item 3 is the T2 SSRF suite (29 tests) still passing with an org host allowed.
- **A dev or test build still reaches any public host.** This unit *adds* hosts; it never takes any away. The
  allowlist is enforced only on the public deployment, exactly as in WP16·1.
- **The host store, the resolver and the secret store are injectable ports.** The host-policy and console suites
  need no database and no network, which is the WP14b/WP19 deps pattern rather than a new one.
- **The console's money connectors are dry runs, not a `mock: true` flag.** The alternative — letting the console
  execute a `payment_link` against a run it invented — is how a debugging aid becomes a way to create checkouts.
