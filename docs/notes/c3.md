## 2. Review decisions

A Sonnet adversarial review checked every export under `src/core/contracts/v3/**` field-by-field against SAAS §14

### 2.1 [blocking, accepted and fixed] `E_BUSY` was missing from `V3_ERROR_STATUS`

**Verified against the spec, not taken on trust.** This is *not* a WP19 transcription slip — it is an inherited
spec inconsistency:

- SAAS §14's code block (the one WP19 transcribed) lists 13 codes and stops at `E_BILLING_UNAVAILABLE`.
- SAAS's own v3.1 review pass (**§17 item I3**) added a **mandatory `503 E_BUSY`** for the global compile bucket
  in front of `POST /blueprints/validate` and `POST /relays/:id/compile` — stated in **§6.4** ("429 →
  `E_RATE_LIMITED` …; 503 → `E_BUSY` with `Retry-After`"), in **§10.4** (`VALIDATE_GLOBAL_RPS`, default 20/s
  burst 40, checked before the per-ipKey limit and before the body is parsed), and in the **Threat Table's**
  CPU-exhaustion row. §7's intro names it as one of WP22's required "v3.1 additions to the owning WPs".
- **§14 was never synced to that prose**, so `grep -rn E_BUSY src/ tests/` had no hits anywhere.

Consequence if left: `SaasError`'s constructor takes `code: V3ErrorCode`, a closed union, so WP22's
`throw new SaasError("E_BUSY", …)` would have been a **hard TypeScript error** — loud rather than subtle, but a
blocker for a WP that is explicitly tasked with throwing it, against a contract that freezes at C3.

**Fix (additive, TASKS-v3 §2 rule 12 — no existing consumer or test affected):** `E_BUSY: 503` added to
`V3_ERROR_STATUS` in `src/core/contracts/v3/errors.ts`, with a comment pointing at §6.4/§10.4 and recording *why*
§14 disagrees. **`docs/SAAS.md` §14's code block was synced in the same commit**, so the code and the spec cannot
drift apart again — that is the one modified file in this merge. Two tests were added: the §14 exact-map
assertion now includes `E_BUSY`, and `saasErrorResponse` is asserted to produce `503` + `Retry-After: 1`, the
exact shape WP22's bucket will throw.

### 2.2 [minor, accepted — documented, not changed] `ValidateRequestV1`'s `blueprint` branch is unbounded

The `source` branch caps at `MAX_SOURCE_BYTES` (256 KiB) via `.max()`; the `blueprint` branch is `z.unknown()`,
which has no cheap `.max()`. §6.2/§10.4 require the cap on **both**. Deliberately **not** fixed in the schema:
a schema-level check would run *after* the body is parsed, while §10.4 requires the bound *before* parsing — the
same reason the compile bucket of §2.1 sits in front of the route at all. Fixing it in zod would give a false
sense of coverage and would also change a name/shape that freezes at C3.

Instead the obligation is written on the schema itself, where WP22 (which owns `public-api.ts` from C3) will read
it: **enforce `Content-Length`/stream length ≤ `MAX_SOURCE_BYTES` at the route/transport layer for both branches,
answering `E_VALIDATION`; the schema is the second line only.**

### 2.3 [minor, accepted and fixed] The "contracts v3 stays pure" guard had a relative-path blind spot

`tests/unit/server/saas/boundaries.test.ts` matched only specifiers starting `node:`, `@/(server|client|app|
components)`, `server-only` or `client-only`. A future `from "../../server/db"` inside `src/core/contracts/v3/*`
would have passed — and relative cross-imports are **already idiomatic in that very directory** (`events.ts`
imports `"../case"` and `"../takeover"`), with five more WPs still to add to `contracts/v3/**` additively before
this is reviewed again. A browser-safety guard that can be walked past by the directory's own house style is
worth little.

**Fix:** the guard now extracts every import/require specifier, resolves the relative ones against the importing
file, and fails anything landing outside `src/core/**`. A companion self-test proves the detector fires
(`../case` → `src/core/contracts/case` passes; `../../../server/db` → `src/server/db` is flagged), so the guard
cannot silently rot into a no-op. The bare-specifier deny-regex is unchanged.

### 2.4 [informational, accepted as-is] `AuditAction` is a closed union

`AUDIT_ACTIONS as const` rather than §14's literal `string & {}` sketch. Intentional, already recorded as
Decision 1 in `docs/notes/wp19.md`, identical value set to §9's 36 actions, and a net type-safety win; the
reviewer agreed and asked for no change. The accepted tradeoff stands: a later WP adding an action needs a
one-line update to any exhaustive `switch`.
