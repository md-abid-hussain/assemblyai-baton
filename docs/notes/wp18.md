### Decisions

1. **Published runs use the stored agent** (§8.3 steps 1–3, exactly as probed). The inline fallback (P-1/P-3 FAIL path) stays unbuilt unless G3 shows otherwise.
2. **The published prompt carries an in-band step rule.** WP18·1 compiles it into the published `system_prompt` and every runtime update: "When a tool result contains a field named next_step, your very next reply must do exactly what next_step says. It replaces the current stage goal."
   - The probe put this rule in its prompt, and P-3's pass depends on it.
   - The real gateway puts `next_step` at the top level of the JSON body. postman-echo had it under `args`, and the model followed it there too.
3. **Gateway contract from P-2:**
   - The request body is the raw args object.
   - No AssemblyAI id header arrives, so the gateway binds a call to the publication's active run and dedupes on the args hash.
   - Don't key anything on `user-agent`.
4. **The F6 audit (v2.1)** accounts for every session on the account, whatever its marker. It matches a session through these routes, in order:
   1. `registry`: a `live_sessions` row with the provider session id.
   2. `takeover`: `takeovers.va_session_id`.
   3. `publication`: `agent_id` in `/v1/sessions` equals a publication's agent. Only one running session per active run counts. An ended session of a known publication agent counts too.
   4. `dev_lease`: an open `live_sessions` VA row with a dev deploy id (`dev-*`, `dev`, `local`, `vercel-*`) and no provider id yet.
      - This match is **count-matched**: one lease covers one running session created within [lease − 15 s, lease + 10 min].
      - Greedy matching, which is optimal here.

   Anomalies:
   - `unknown_session`: this deploy's marker, running or ended, with no match through routes 1–3 (v2.0 behaviour; a dev lease never covers the prod marker).
   - **`unregistered_session` (new)**: any other **running** session with no match through routes 1–4.
   - `running_but_closed`: now applies to every marker.
   - `over_concurrency`: now counts every running session on the account. Rows closed within the 60 s grace are not counted, because the provider lags `session.end` by a few seconds.

   **Any anomaly trips `replay_only`.** Sessions younger than 90 s are not flagged yet (`inGrace`).
5. **Publications are read from `relay_publications` directly** (`readPublishedAgents`, guarded by `to_regclass`). Until WP14b's migration 0001 exists the list is empty, and once it lands the audit uses it with no wiring. Tests and WP18·2 can inject `Wp8Ports.publishedAgents`.
6. **The report type widened.** It is now `VaAuditReportV21` (in `ext/wp18-audit.ts`), a superset of WP8's `VaAuditReport` with the new anomaly kind plus `accountRunning`, `matched`, `devLeases` and `inGrace`. `registerVaAuditHook` takes `() => Promise<unknown>`, so WP12's runner and cron are unaffected. `ext/wp8-verify.ts` is unchanged.

### Decisions

1. **The gateway answers HTTP 200 with a status body** for `no_active_call`, `not_available`, `unavailable`,
   `failed` and `bad_arguments`. That body is what the agent reads; a non-2xx would only make it apologise. A **bad
   key is a real 401** and an unknown publication or malformed tool name a 404 — the asymmetry TASKS-v2 acceptance 3
   describes.
2. **The publication key rotates on every republish, and its new hash is written in the same statement that swaps the
   new agent in.** A hash cannot be put back into an agent definition, so a stable key is impossible; ordering it this
   way means the old agent and its old key keep working until the moment they are replaced, and a failed create
   changes nothing.
3. **A superseded agent goes to a tombstone row** (`status:'deleting'`, `share_slug: retired-…`, the old agent id),
   deleted immediately and **retried by the purge job** if that fails (P§8.1 step 4). No new table, and the F6 audit
   keeps recognizing the agent while it exists.
4. **`stageSeq` = the index of the stage in the blueprint's stage order.** Stages are forward-only, so it only grows —
   the contract's "increments on every stage change" with no extra column to keep in step.
5. **Per-visitor publishes a day follow SAAS, not P§8.4's "1 per day per visitor".** SAAS §1 keeps only "the global 25
   live agents and 10 publishes a day" as hard stops and moves the per-workspace number to the plan
   (`livePublications`, guest 1). A visitor bucket of 10/day stays as a safety net. A daily limit of 1 would have
   blocked the *republish* that the demo and "Try an edit" depend on.
6. **`configRedacted` has two fidelities.** The publish response and the share page carry the full redacted create
   body (it needs a compile); `RelayDetail.publication`, a hot read, carries the structural config (names, gateway
   URLs, header names) rebuilt from the blueprint with no compile.
7. **Published runs stay on `transcription_mode:"balanced"`** for the whole run (P§8.1 fixes it at create; the state
   route reports it). The in-band `next_step` is the stage-change mechanism, so nothing here needs the per-stage
   input mode.
8. **A create refusal is classified** (`createAgentError`): 4xx other than 408/429 → `E_VA_CONFIG` naming the app URL,
   everything else → `E_VA_TRANSIENT`. See [VERIFY] below for why.
9. **Publishing needs a public `APP_URL`** and refuses with 503 `E_MAINTENANCE` without one.
