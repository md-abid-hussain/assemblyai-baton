### Decisions

1. **`AuditAction` is a closed union of the §9 list, not `string & {}`.** §14 sketches the type as `string & {}`
   with the comment "exactly the §9 list"; the union *is* that list with the compiler checking it, and adding an
   action later is additive. The literal `string & {}` would accept any string, which is the opposite of a contract.
2. **`requirePrincipal` goes through the port.** `ports.ts` ⇄ `principal.ts` is a lazy ESM cycle (a hoisted function
   declaration, referenced only inside the getter), which is why `resolveLegacyPrincipal` is a `function` and not a
   `const`. The payoff: WP19·2 registers the session/API-key resolver and **no route file changes**.
3. **The same-origin check applies to `kind === "session"` only.** §3.9 says "our session-authenticated non-GET
   routes". Applying it to visitors would break v2: a cross-origin POST from a device is allowed today, and the
   test asserts it still is. API-key requests never read cookies and are exempt by the same rule.
4. **`isAnonymous` means an anonymous *account*** (the Better Auth anonymous plugin), not "no account at all". A
   visitor has `userId: null, isAnonymous: false`, and `account: true` refuses on `userId === null || isAnonymous`,
   so both are covered without overloading the flag.
5. **The default `Entitlements` is real, not a stub.** Limits come from `PLANS`; the plan comes from a swappable
   resolver (`ws_…` → guest, anything else → free) until WP21's `org_entitlements` exists; counts come from
   `setOrgCounter(key, fn)`, which owners register (`relays` → WP14b, `secrets` → WP16, …) and which reads 0 when
   unregistered, so no WP is blocked by another's absence; rates come from the registered `UsageMeter`. Simulated
   minutes do **not** draw on the monthly allowance (§4.5), only recorded and published ones do.
6. **`public-api.ts`: names frozen, fields deliberately thin.** The models WP22 owns the detail of (`RelayDetailV1`,
   `RunV1`, `CaseV1`, `UsageV1`, …) are `z.looseObject`, so WP22's richer real responses validate and every addition
   is additive. The shapes §6.2/§6.3 spell out in full (`ErrorV1`, `PageOf`, `MeV1`, `RelaySourceV1`,
   `CreateRelayV1`, `SaveSourceV1`, `SaveDraftV1`, `ValidateRequestV1`) are exact. Request bodies keep the spec's
   camelCase (`expectedRev`, `relayId`); wire payloads are snake_case.
7. **The default `RelaySourceStore` is read-only and empty** (`get` → `null`; `save`/`create` throw
   `E_UNPROCESSABLE`). §14 describes it as "serializes the canonical draft (read-only)", but the relay registry is
   WP14b's and is not in WP19's scope at C3, so serializing would mean importing across an ownership line. WP14b·4
   registers the real store; the behaviour difference is only "no source yet" versus "the draft's source".
8. **`src/server/env.ts` is untouched** (WP12's). `TENANCY_MODE` and `CONNECTOR_HOST_ALLOWLIST` are read from
   `process.env` directly with safe defaults (`legacy`, empty). If WP12 wants them in `EnvSchema`, that is a
   one-line request file; nothing here depends on it.
9. **`trustedOrigins`: passing the `appUrl` key overrides the environment**, including passing it as `undefined`,
   which is how a caller says "there is no APP_URL" without mutating `process.env`. Same for `errorDocsUrl`, which
   keeps the ordinary default-parameter behaviour instead.
10. **Additive helpers beyond the §14 listing** (all new names, nothing renamed): `assignableRoles`,
    `AUDIT_ACTIONS`, `AUDIT_SOURCE_SAVED_COALESCE_MS`, `EVENT_DATA_SCHEMAS`, `CodecCode`, `PAGE_LIMIT_DEFAULT/MAX`,
    `PUBLIC_API_VERSION`, `V3_ERROR_CODES`, `isV3ErrorCode`, `tenancyMode`, `requestIdOf`, `startPathFor`,
    `deviceOf`, `checkSameOrigin`, `setOrgCounter`, `setPlanResolver`, `resetSaasPorts` and the three
    `createMemory*` factories.

## C3 review fixes (integrator, post-review)

A Sonnet adversarial review of WP19·1 checked every `contracts/v3/**` export field-by-field against SAAS §14 and
its source sections. Three findings were accepted and fixed in `wp19: C3 review fixes`; the fourth needed no code.

1. **[blocking] `E_BUSY` was missing from `V3_ERROR_STATUS`.** Not a transcription slip: SAAS §14's code block
   predates the v3.1 review pass, which added a mandatory `503 E_BUSY` shed for the global compile bucket in
   front of `POST /blueprints/validate` and `POST /relays/:id/compile` (§6.4 line "429 → `E_RATE_LIMITED` …
   503 → `E_BUSY`", §10.4, the Threat Table's CPU-exhaustion row, and §17 item I3) but never synced §14. WP19
   transcribed §14 faithfully, so the code WP22 is explicitly tasked with throwing did not exist — and since
   `SaasError`'s constructor takes `code: V3ErrorCode`, WP22's `throw new SaasError("E_BUSY", …)` would have been
   a hard TypeScript error, not a subtle bug. Fixed additively (TASKS-v3 §2 rule 12): `E_BUSY: 503` added to the
   map, `docs/SAAS.md` §14's block synced in the same commit so code and spec cannot drift apart again.
2. **[minor] `ValidateRequestV1`'s `blueprint` branch carries no size bound.** The `source` branch caps at
   `MAX_SOURCE_BYTES`; `blueprint` is `z.unknown()`, which has no cheap `.max()`, and a schema-level check would
   run *after* the body is parsed anyway — while §10.4 requires the bound *before* parsing, for the same reason
   the compile bucket sits in front of the route. Documented as an explicit WP22 route/transport-layer
   obligation on the schema itself, where WP22 will read it. No schema change (the names are frozen at C3).
3. **[minor] The "contracts v3 stays pure" guard had a relative-path blind spot.** It matched only `node:`,
   `@/(server|client|app|components)`, `server-only` and `client-only`, so a future `from "../../server/db"`
   would pass — and relative cross-imports (`../case`, `../takeover`) are already the idiomatic style in this
   directory, with five more WPs still to add to it additively. The guard now also resolves every relative
   specifier and fails anything landing outside `src/core/**`, plus a self-test proving the detector fires.
4. **[informational] `AuditAction` is a closed union, not §14's `string & {}` sketch.** Kept as-is — this is
   Decision 1 above, the value set is identical to §9, and the reviewer agreed it is a net type-safety win.

### Decisions

1. **`...(apiKeyPlugins() as [])`, not a bare spread.** Both stubs are `unknown[]` (they must stay
   dependency-free). Spreading `unknown[]` into `plugins: [...]` widens the element type to `unknown`, and Better
   Auth infers `auth.api` from the array type — so it collapses inference for the **whole array**, not just those
   entries: `signInAnonymous` and `session.activeOrganizationId` vanish. That was 5 of the 9 typecheck errors the
   interrupted attempt left behind. Verified both ways with a throwaway probe before choosing the cast. The cost
   is recorded in `docs/notes/requests/wp19-to-wp21-wp22.md`.
2. **`verification` is mapped to `auth_verifications`.** `usePlural: true` wants `verifications`, which v2's
   `0000_init` already owns. v2's schema is frozen, so Better Auth's name is the one that moves. This is §16 row
   (a)'s documented fallback, applied for a reason §16 did not anticipate — a name collision, not an adapter
   problem.
3. **`schema.ts` carries more than the one re-export line the §6 carve-out allows.** SAAS §2.4 puts org columns on
   *existing* v2 tables, and drizzle-kit generates from the schema, so `cases.org_id` can only be declared where
   `cases` is. All additive and nullable. Flagged to WP14b rather than done quietly.
4. **Audit rows go through the `AuditWriter` port, whose default is in-memory.** The DB writer is WP19·3's
   deliverable, so the tests assert on the port rather than on `audit_log`; `0003`'s trigger has its own test.
5. **A refused anonymous sign-in degrades, it does not throw.** `/api/guest/start` is on the judged path and must
   never look like an outage.

### Three bugs the tests found

1. **Guest start left the browser org-less for five minutes.** `session.cookieCache` mints `co.session_data` **at
   sign-in**, when the org does not exist yet, so it carried `activeOrganizationId: null`; `getSession` prefers
   that cookie over the database for `cookieCacheMaxAge`, so the row written moments later was invisible. On the
   judged path, "Try it free" would have landed in an org-less `/app`. Fixed by refreshing the cache through the
   organization plugin's set-active, and by emitting **one `Set-Cookie` per name (last wins)** instead of trusting
   every consumer to collapse the stale duplicate the way a browser would.
2. **Better Auth's own `/sign-in/anonymous` limit undercut §3.3.** It was 10/hour/IP — *below* our per-ipKey hourly
   limit and *inside* `signInAnonymous`, i.e. after our own check — so it was the cap that actually applied, and it
   surfaced as a failed start rather than the documented calm fallback. §3.3 explicitly wants a judging panel
   behind one office or VPN egress IP to stay inside the limits; the eleventh judge would have hit an error. Now
   derived from `guestLimits().perIpKeyHourly` plus headroom, so our limiter is the one that speaks.
3. **`declineDeviceClaim` silently did nothing.** `jsonb_set(t, '{claimDeclined,<vid>}', …, true)` creates only the
   **last** path element; with no parent key Postgres returns the document unchanged **and raises nothing**, so
   "not mine" was never recorded and the card came back on the next load. Rewritten as a two-level `||` merge, with
   the visitor id bound rather than interpolated into a `text[]` path literal.

### Four bugs the work found

The first was a failing test on arrival; the rest were found by writing the tests the acceptance criteria ask
for. All four are fixed and covered.

1. **`isUniqueViolation` never returned true** (`src/server/identity/org-store.ts`). It read `code` off the
   error drizzle throws, but drizzle 0.45 wraps a failed query in `DrizzleQueryError` and puts the pg error on
   `cause`. Two costs: a taken slug on `PATCH /api/app/orgs/:id` was a **500 instead of 409**, and — silently —
   `createOrg`'s retry loop gave up on the first collision instead of trying a fresh suffix. The second is the
   one that mattered: guest start and `ensurePersonalOrg` both go through that loop, so a collision on a slug
   that is purely cosmetic would have failed a workspace creation on the judge path. It now walks the `cause`
   chain. Both halves have a test, and I confirmed both fail without the fix.
2. **`member.joined` was a declared `AuditAction` that nothing wrote.** §3.8 deliberately leaves
   `accept-invitation` on Better Auth's own endpoint, because the plugin is what enforces the email match that
   makes a copyable link safe — so no route of ours ever sees an accept. The org's trail showed the invitation
   and then the person's later actions, with the moment they gained access missing. Written now from the
   organization plugin's `organizationHooks.afterAcceptInvitation`, with the invitee as the actor.
3. **No invitation could ever be accepted.** The plugin gates accept/reject on `user.emailVerified` unless it
   recognises the invitation ids as its own opaque ones; it decides that by checking whether
   `advanced.database.generateId` is set, and ours is (`prefixedId`, for the §2.2 prefixes). So the gate turned
   itself on, while `EMAIL_MODE=off` (§3.2) means no verification mail is ever sent and `emailVerified` stays
   false forever. The invite was created, the link resolved, and accepting always returned 403 — the whole of
   §3.6 was dead and nothing caught it, because the only accept test was a negative one. Fixed with
   `requireEmailVerificationOnInvitation: false`, which is sound rather than merely expedient: the check stands
   in for the unguessability of the id, and ours is `nanoid()` — ~126 bits of CSPRNG output. The plugin cannot
   know that about a custom generator; we can. The email match still runs on every accept, gate or no gate.
4. **The copyable link was readable by anyone with `member:read`, down to a viewer.** Following from (3): with
   no address verifiable anywhere in this build, a viewer who could read a pending **admin** invitation's link
   could register that address and accept it — a role escalation with no trace until `member.joined` is already
   written. `listInvitations` now returns `link` only to callers holding `member:invite`; existence, recipient,
   role, inviter and expiry stay visible to everyone who can see the Members page.

### Decisions

- **One non-additive contract edit, against §2 rule 12, made deliberately.** `InvitationView.link` is narrowed
  from `string` to `string?` — the fix for bug 4 needs the field to be absent, and an empty string is the worse
  contract because it is the shape that renders a broken copy button. Blast radius today is zero: no worktree
  consumes `InvitationView`. Recorded in `docs/notes/requests/wp19-to-wp20-invitation-link.md` so WP20 builds
  the Members page against the right shape, and flagged there for the integrator rather than left to be found.
- **The audit-orphan guard is scoped to `org.*`, `member.*`, `guest.*`.** The rest of `AUDIT_ACTIONS` belongs
  to WP17, WP21, WP22 and WP24 and would fail today for the honest reason that those units have not run.
  WP19·4 widens it as they land.
- **The `member.joined` actor is the invitee, not the inviter.** They are the one who acted.
- **A plan lookup that throws falls back to `free`, not to the action failing.** Free is the conservative
  answer for a real org, and an entitlements hiccup should not fail a mutation.
